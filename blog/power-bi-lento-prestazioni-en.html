Slow Power BI report? 5 things to check to improve performance

Slow Power BI reports? Explore five performance bottlenecks—visuals, data models, DAX, connectivity and capacity—and learn how to diagnose them.

THE CONTEXT

A Power BI report can be well designed, feature accurate KPIs and effective visuals, yet still be difficult to use. This happens when pages take too long to load, filters respond slowly, or every interaction involves several seconds of waiting. The problem goes beyond user experience. An unresponsive dashboard interrupts the flow of analysis, makes data exploration more difficult and can undermine trust in the tool. Performance is therefore an integral part of report quality, just like accurate calculations and clear visualizations.

When Power BI becomes slow, the first reaction is often to blame the amount of data. In reality, a model containing millions of rows can perform well, while a report with far fewer records can experience significant delays. The difference depends on several factors: the semantic model's structure, the complexity of DAX measures, the number of visuals, connection mode and available resources.

Before making changes, however, it is important to distinguish between two situations. One is a report that responds slowly during use, for example when someone applies a filter. Another is a data refresh that takes particularly long because of Power Query transformations or the performance of the source system.

These two situations may have different causes. Here are five areas worth investigating when a Power BI report does not deliver the performance you expect.

1. Too many visuals on the same page

One of the most common mistakes is trying to fit every available piece of information into a single dashboard.

KPIs, bar charts, tables, matrices, slicers and detailed visuals are added one after another, with the goal of providing an increasingly complete picture.

The result, however, can be counterproductive.

Each visual can generate a query against the semantic model. When someone changes a filter, multiple elements on the page may need to be recalculated.

The issue is therefore not simply the number of charts, but the total amount of work required to update them.

A page with many complex visuals may demand more resources than one whose structure has been planned more carefully.

1. What can you do?

Before adding another element, ask whether that information is really needed in the main view.

Secondary analyses can live on dedicated pages, while drillthrough lets users explore details only when they need them.

Interactions between visuals also deserve attention: not every chart necessarily needs to respond to every selection.

Removing unnecessary elements can improve performance, but it has another advantage too.

A more focused dashboard is often easier to read and interpret.

It is the same principle behind data storytelling: every element should serve a clear purpose rather than simply occupy space because the data is available.

2. An inefficient data model

Power BI performance depends heavily on how the data is organized.

A model with complex relationships, unnecessarily large tables or complicated filter paths can make queries more expensive to execute.

Imagine a sales model containing information about sales, customers, products and dates.

A well-designed structure clearly separates the events being analyzed from the information used to filter them.

This is the principle behind the star schema.

The fact table contains events such as sales transactions.

Dimension tables describe customers, products, dates and other attributes that are useful for analysis.

This organization makes the model easier to understand and can improve query efficiency.

2. What can you do?

Check relationship cardinality, look for unnecessary tables and columns, and pay attention to bidirectional filtering.

Bidirectional filters can be necessary in specific scenarios, but using them without a real need can increase the work required of the model.

Granularity matters too.

If the analysis requires aggregated monthly figures, it is not always necessary for every visual to work through individual transactions.

The key point is that performance optimization does not begin with the charts: it begins with the design of the semantic model.

3. DAX measures that are more complex than necessary

DAX makes advanced calculations and dynamic analysis possible, but not every formula requires the same amount of work to execute.

Functions such as CALCULATE, FILTER and SUMX are essential in many models.

Their use, however, should match the calculation you actually need.

Consider an example.

If a Sales table already contains a column with the amount of each transaction, the total can be calculated directly:

Total Sales =
SUM(Sales[Sales Amount])

If the value instead needs to be calculated by multiplying quantity by unit price, we can use:

Total Sales =
SUMX(
    Sales,
    Sales[Quantity] *
        Sales[Unit Price]
)

Both formulas can be correct, but they apply to different data structures.

When the value to aggregate is already available and reliable, a direct sum avoids recalculating an expression for every row.

That does not mean SUMX is a function to avoid.

It means choosing the most appropriate DAX pattern for the problem.

3. What can you do?

Review measures that iterate over very large tables, inspect complex filters and look for unnecessary repeated calculations.

Using variables can make formulas easier to read and, in some cases, avoid redundant evaluations.

For deeper analysis, tools such as DAX Studio can help you examine query execution.

The goal is not to write shorter formulas, but to build measures that are correct, readable and efficient.

4. Connection mode and data management

Another important factor is how Power BI accesses the data.

With Import mode, data is loaded into the semantic model and queries can take advantage of its internal storage engine.

With DirectQuery, many operations instead require queries to the underlying data source.

This means performance may also depend on the speed of the database and the complexity of the queries it receives.

If the source responds slowly, visuals may take longer to update as well.

With Import mode, a different issue can arise during refresh.

Costly Power Query transformations, large data volumes and steps that prevent query folding can increase refresh times.

When supported, query folding delegates some transformations directly to the source, avoiding unnecessary processing in the Power Query engine.

4. What can you do?

First determine whether the slowdown affects interaction with the report or data loading.

In the first case, check the connection mode and query performance.

In the second, examine Power Query steps, remove unnecessary columns and consider incremental refresh strategies where appropriate.

The distinction matters: optimizing the refresh of an Import model does not necessarily make navigating the dashboard faster.

5. Available resources and execution environment

Not every performance problem originates inside the Power BI file.

A report may work correctly in Power BI Desktop but feel less responsive once published to the service.

In these cases, possible causes include available resources, the number of concurrent users, network conditions or characteristics of the hosting environment.

For DirectQuery models, the gateway and source system may also play a role.

It is therefore important not to assume that every slowdown is caused by DAX measures.

5. What can you do?

Compare how the report behaves in Desktop and in the service, trying to keep testing conditions similar.

Check whether the problem occurs consistently or only at certain times of day.

Where available, Microsoft Fabric capacity monitoring can help identify periods of resource pressure.

A report can be designed correctly and still be affected by the limits of the infrastructure hosting it.

For this reason, performance analysis should consider the entire solution, not just the visualization layer.

IN PRACTICE

How to find out what is really slowing down a report

1. Measure performance

Understanding the possible causes is useful, but the most important step is identifying what is actually happening in your report.

Power BI provides a specific tool for this: Performance Analyzer.

In Power BI Desktop, open it from the Optimize ribbon by selecting Performance Analyzer.

The process is straightforward:

  1. Open the report page that feels slow.
  2. Select Start recording.
  3. Select Refresh visuals or reproduce the interaction causing the problem.
  4. Expand the recorded visuals to examine their timings.
  5. Identify the element that needs the most attention.

2. Interpret the timings

For each visual, the tool separates several components.

DAX query indicates the time required to retrieve query results from the semantic model.

Visual display is the time needed to render the result on screen.

Direct query, when present, shows the time spent querying external data sources.

Other covers tasks such as query preparation, waiting and additional processing.

Timings need to be interpreted carefully because they can include waiting caused by other activity on the page.

3. Examine a practical example

Consider an example.

Imagine a sales dashboard with several KPI cards, a sales trend chart and a detailed matrix by product.

When someone changes the date filter, the page feels slow.

Using Performance Analyzer, we discover that the matrix takes much longer than the other visuals.

If most of the time is spent on the DAX query, we may need to investigate the measures, the number of groupings requested or the model structure.

If the time is concentrated in visual display, it may be better to check the matrix's complexity and the number of elements it must render.

That difference matters.

Without this analysis, we could spend time optimizing formulas that are not the root cause of the problem.

A sound approach is to measure performance, change one element at a time and repeat the test.

Only by comparing results before and after a change can we determine whether it truly helped.

DAY-TO-DAY IMPACT

What really changes in day-to-day work

Working on performance changes how reports are designed and maintained.

Before adding a new visual, it becomes useful to consider how much it contributes to the analysis.

Before building a complex measure, we should check whether a simpler solution fits the model better.

Before blaming data volume for a slowdown, we should identify where the bottleneck actually is.

These checks are not just for developers.

A responsive dashboard allows people to explore data more continuously, compare scenarios and investigate information without interruptions.

Performance therefore influences how effectively insights are communicated.

If a report is slow, the problem is not merely technical: it can become an obstacle to using data in decision-making.

IN SUMMARY

In summary

A slow Power BI report is not necessarily the result of a dataset that is too large. The causes may lie in the number of visuals, the model structure, DAX measures, connection mode or the environment in which the report runs.

There is no single solution that works in every situation. The starting point should always be measuring performance, using tools such as Performance Analyzer to identify what needs attention. Optimizing Power BI does not mean removing useful features or giving up analytical depth.

It means designing a solution in which data, calculations and visuals work together as efficiently as possible. Because an effective dashboard must do more than display the right information. It must allow people to access, explore and understand that information without barriers.
